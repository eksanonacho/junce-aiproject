## 一、AI 初诊项目定位

### 1.1 项目是什么

> 来源：PROJECT_CONTEXT.md

君册财税打包开发两个软件项目：

1. **内部管理小程序**（对内）：财税公司的内部管理系统（OA + 轻量 CRM + 任务流转），管理客户从入库到出库的全生命周期。**当前主力开发对象，后端已封板。**
2. **AI 财税合规初诊系统**（对外）：客户上传财税资料 → AI 自动分析 → 输出诊断报告的获客工具。**暂缓，等客户提供九维度规则后再开发。**

### 1.2 与小程序的关系

> 来源：PROJECT_CONTEXT.md、DEPLOYMENT_GUIDE.md、junce_requirements_v2.md

| 维度 | 说明 |
|---|---|
| 开发顺序 | 错峰开发，先小程序后 AI。小程序后端已封板（12 模块、55 接口、63/63 回归通过） |
| 部署 | 两个项目共用同一台服务器，Docker 容器隔离运行 |
| 服务器 | 以君册名义注册，开发方代管。首年含在合同总价内，第二年起客户自续 |
| 数据 | 预留打通接口，AI 初诊收集的客户可导入小程序客户档案 |
| 代码 | 独立仓库、独立开发、独立部署 |

### 1.3 小程序已有可复用数据

> 来源：API_CONTRACT.md、.docs、junce_requirements_v2.md

小程序 `customers` 表已沉淀的客户字段，AI 初诊可直接复用：

| 字段 | 用途 |
|---|---|
| companyName（企业名称） | 报告抬头、客户识别 |
| industry（行业） | 行业风险判断 |
| registerDate（注册时间） | 经营年限判断 |
| taxType（税务类型） | 小规模/一般纳税人规则不同 |
| region（区域） | 区域性政策差异预留 |
| annualRevenue（年流水，Decimal 12,2） | 规模判断、税负评估 |
| staffCount（人员数） | 社保、个税合规判断 |
| companyType（一人/多股东/个体户） | 风险画像 |
| customerCategory（新用户/代理户） | 初始状态判断 |
| tier（VIP/优质/中低/零申报） | 客户管理优先级 |

小程序已有 15 个服务类型，AI 初诊可对应推荐：
注册、地址、开户、变更、注销、代理、社保、公积金、进出口备案、食品证、道路运输证、卫生证、代理记账、财务外包、合规项目

## 五、风险分析中与 AI 相关的部分

### 5.1 产品风险

> 来源：RISK_ANALYSIS.md、CTO_NOTES.md

| 风险 | 说明 |
|---|---|
| **AI 九维度规则未给** | 整个 AI 初诊项目卡在这里。客户在"打磨"。**AI 工期从收到规则那天才算，别让它无限期拖着尾款。** |
| 需求范围膨胀 | 纪姐可能继续加需求。任何新需求先判断属于一期还是二期，守住边界。 |
| 客户需求反复 | 纪姐决策易受同行/外界影响，可能中途改方向。关键需求需落到书面确认。 |

### 5.2 部署风险

> 来源：RISK_ANALYSIS.md、DEPLOYMENT_GUIDE.md

| 风险 | 说明 |
|---|---|
| 服务器以客户名义注册 | 购买、实名、备案需客户配合。尽早让客户提供资料。 |
| Docker 环境差异 | 本地 Colima 环境与生产服务器可能不一致。部署前用 docker-compose 在类生产环境演练。 |
| 文件上传存储增长 | AI 初诊报告如有附件上传，存储会持续增长。需提前设计存储策略。 |

## 七、技术约束（适用于 AI 初诊）

> 来源：CLAUDE.md、junce_requirements_v2.md、junce_requirements.md

| 约束 | 说明 |
|---|---|
| **金额字段** | 一律 Decimal(12,2)，禁止 float，禁止 Prisma 默认 Decimal(65,30) |
| **部署方式** | Docker 容器化，与小程序共用服务器、容器隔离 |
| **数据库** | PostgreSQL（可与小程序共用实例、不同库） |
| **认证** | JWT（内部后台）；客户侧无需登录（手机号验证即可） |
| **开源模板** | 仅用 MIT / Apache-2.0 协议，禁用 GPL |
| **数据安全** | 客户财税数据加密存储，传输 HTTPS，操作日志可追溯 |
| **服务器** | 以君册名义注册，首年含在合同内，第二年起客户自续 |

## 八、小程序开发中的经验教训（AI 初诊可借鉴）

> 来源：.docs、CLAUDE.md

| 经验 | 对 AI 初诊的启示 |

## 九、部署架构（AI 初诊 + 小程序共享）

> 来源：DEPLOYMENT_GUIDE.md

```
        用户（浏览器/微信）
              │  HTTPS
              ▼
    ┌───────────────────┐
    │   Nginx 反向代理    │  HTTPS 证书 / 域名 / 转发
    └─────────┬─────────┘
              │
    ┌─────────┴──────────────┐
    ▼                        ▼
┌──────────┐  ┌──────────┐  ┌──────────────┐
│ 小程序 API │  │ AI 初诊  │  │ 静态资源     │
│ (容器)    │  │ API(容器) │  │ (Nginx 托管) │
└─────┬─────┘  └─────┬────┘  └──────────────┘
      │              │
      └──────┬───────┘
             ▼
    ┌──────────────┐
    │ PostgreSQL   │ (容器 + 数据卷)
    │ 小程序库 +   │
    │ AI 初诊库    │
    └──────────────┘
```

要点：
- 同一台云服务器，三个容器（小程序 API、AI 初诊 API、PostgreSQL），Nginx 做统一入口
- 两个项目不同数据库（如 `junce_miniprogram` 和 `junce_ai_diagnosis`），数据隔离
- 如需数据打通，通过 API 调用，不直接跨库查询
