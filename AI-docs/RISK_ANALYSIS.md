## 一、需求与客户风险（当前最大风险源）

### 风险 1.1：核心诊断规则迟迟不到位（🟢 已缓解）

- **描述**：九维/四维规则、风险标准、场景库等核心资料由纪姐提供，原本全部缺失。
- **当前状态**：V2 已不再等待客户资料。基于行业通用财税知识和项目经验，自作主张构建了完整的九维规则体系（65题/55规则/12场景）和四维看板引擎。系统已可独立运行演示。
- **剩余风险**：纪姐可能对自建规则有不同意见，需要微调。但核心框架和计算逻辑已稳固，调整成本低（seed 数据修改即可）。
- **应急**：如纪姐提供正式规则，替换 seed 数据即可，不涉及代码改动。

### 风险 1.2：需求范围膨胀

- **描述**：纪姐可能不断加需求——"能不能加上 XX 功能""我看了别家的 AI，人家还能做 YY"。已在小程序开发中多次发生（小程序、文案、企业微信不断加码）。
- **出现时机**：资料对接、产品原型评审、开发过程中。
- **影响范围**：工期失控、亏本。
- **规避**：
  - 严守第一版 MVP 范围（已明确"第一版做什么、不做什么"）
  - 第一版不做：完全自动专业结论、自动报价、复杂多轮 Agent、后台规则编辑器
  - 任何新需求先判断属于一期还是二期，援引合同二期边界
- **应急**：超范围功能列入二期，另行报价。

### 风险 1.3：客户需求反复

- **描述**：纪姐决策易受同行/外界影响，可能中途改方向（如"四维改九维""九维改四维""问卷要全部重来"）。
- **出现时机**：任意阶段。
- **影响范围**：返工、拖延。
- **规避**：关键需求落到书面（微信确认 + 文档）；开发前确认范围。
- **应急**：已确认的范围有据可查，变更走"需求变更"流程。

## 二、产品风险

### 风险 2.1：AI 输出不当导致合规风险（🔴 高）

- **描述**：AI 可能在报告中说出不恰当的话——"违法了""必须补税""保证解决""税局不会查"——导致法律纠纷或声誉损失。
- **出现时机**：报告生成模块上线后。
- **影响范围**：客户投诉、法律风险、君册声誉受损。
- **规避**：
  - 提前明确禁用话术清单（已提供 15 条建议）
  - 所有高风险报告必须人工复核后才能给客户
  - 每份报告强制附加免责声明
  - 规则引擎输出做关键词过滤 + 安全表达替换
- **应急**：发现不当输出立即人工介入、修改报告、补充禁用词库。

### 风险 2.2：诊断质量不达预期

- **描述**：九维/四维规则不完善、场景库覆盖不全，导致 AI 诊断"不像君册""还没有人工判断准"。
- **出现时机**：规则引擎开发完成后、客户试用时。
- **影响范围**：客户不认可 AI 初诊价值、商务转化率低。
- **规避**：
  - 规则由纪姐提供，不是我们编——输出质量上限由资料质量决定
  - 第一版明确"初筛"定位，不做"终判"
  - 保留人工复核兜底
- **应急**：收集中途试用反馈，持续补充规则和场景库。

### 风险 2.3：AI 初诊被误解为"全自动专业诊断"

- **描述**：客户可能认为 AI 初诊 = 可以替代会计师/税务顾问的完整诊断，产生不合理期待。
- **出现时机**：对外发布后。
- **影响范围**：客户投诉"不够专业""太简单"。
- **规避**：
  - 网站和报告明确标注"初步风险筛查""不构成最终专业意见"
  - 每份报告强制免责声明
  - 不给最终专业结论，只给"建议关注""建议复核"
- **应急**：在报告和网站上加强定位说明。

## 三、技术风险

### 风险 3.1：规则引擎复杂度超预期

- **描述**：如果九维/四维的检查项、判断标准、风险叠加规则非常复杂，硬编码可能难以维护，后期可能需要规则引擎框架或 DSL。
- **出现时机**：规则引擎开发时。
- **影响范围**：开发周期延长、代码复杂度上升。
- **规避**：
  - 第一版采用"配置文件 + 代码逻辑"的简单方式
  - 不追求可视化规则编辑器（二期做）
  - 先支持最核心的判断逻辑，边缘 case 标记人工复核
- **应急**：复杂度确实高时，评估引入轻量规则引擎（如 json-rules-engine）。

### 风险 3.2：前端兼容性（手机 + PC 双端）

- **描述**：AI 初诊网站需同时适配手机端（客户填写问卷）和 PC 端（内部后台查看报告），响应式适配可能出现问题。
- **出现时机**：前端开发中后期。
- **影响范围**：某一端体验差。
- **规避**：优先以手机端为主要测试端（客户侧）；PC 后台用独立布局。
- **应急**：分端针对性修样式。

### 风险 3.3：PDF 导出技术选型

- **描述**：报告 PDF 导出如果要求复杂排版（Logo、页眉页脚、盖章区域、雷达图），技术选型不当会导致返工。
- **出现时机**：报告模块开发时。
- **影响范围**：PDF 效果不达预期。
- **规避**：
  - 第一版先做简洁文字版 PDF
  - 提前确认纪姐对 PDF 的最低要求（是否必须有图表、盖章区）
  - 选型时考虑 Puppeteer / jsPDF / 服务端渲染方案
- **应急**：先交付 HTML 版报告，PDF 延后优化。

## 四、部署与运维风险

### 风险 4.1：与小程序共用服务器的资源竞争

- **描述**：两个项目共用一台服务器，Docker 容器隔离但共享 CPU/内存/磁盘。如果 AI 初诊调用大模型 API 或生成大量 PDF，可能影响小程序正常运行。
- **出现时机**：部署上线后，使用量增大时。
- **影响范围**：小程序响应变慢或不稳定。
- **规避**：
  - Docker 设资源限制（CPU/memory limits）
  - AI 初诊的 LLM API 调用做超时和限流
  - 监控服务器资源使用
  - 评估是否需要独立服务器
- **应急**：临时扩容或迁移到更高配置服务器。

### 风险 4.2：LLM API 依赖与成本

- **描述**：AI 初诊如果调用大模型 API（用于 FAQ 回答、报告生成），产生 API 费用且依赖外部服务可用性。
- **出现时机**：开发阶段和上线后。
- **影响范围**：运营成本、服务可用性。
- **规避**：
  - 第一版以规则引擎为主，FAQ 用预置标准回答，减少 LLM 依赖
  - 如需 LLM，评估成本上限和降级方案
  - API key 做额度限制
- **应急**：LLM 不可用时降级为规则回答。

## 五、V2 新增风险（2026-06-23）

### 风险 5.1：自建规则与纪姐预期不一致

- **描述**：V2 的 55 条规则和 65 题问卷是自主构建的，纪姐可能认为"不够君册"或与她的经验不符。
- **出现时机**：纪姐第一次看到 V2 演示时。
- **规避**：规则全部通过 seed 数据配置，修改不涉及代码。只需调整 seed 文件中的文字和条件。
- **应急**：将纪姐反馈逐条映射到 DiagnosisRule 的修改，批量替换 seed 后重新部署。

### 风险 5.2：ECharts 包体积过大

- **描述**：ReportPage chunk 1.1MB（ECharts 全量引入），影响移动端加载速度。
- **出现时机**：移动端客户访问报告页时。
- **规避**：后续改为按需加载（仅引入 radar 图表：`echarts/lib/chart/radar`）。
- **应急**：可接受当前体积用于第一期演示（WiFi 环境下影响不大）。

### 风险 5.3：资料上传存储增长

- **描述**：`uploads/` 目录存储客户上传的 PDF/Excel/Word/图片，长期运行会占用大量磁盘。
- **出现时机**：上线后客户使用量增大时。
- **规避**：当前本地存储仅用于开发/演示。生产环境建议迁移到对象存储（S3/OSS）或定期清理。
- **应急**：设磁盘告警，定期清理测试数据。

### 风险 5.4：SubmissionAccessToken 无过期机制

- **描述**：当前 `Submission.accessTokenHash` 没有 expiresAt 字段，token 永不过期。
- **出现时机**：token 泄露后长期有效。
- **规避**：后续增加 `accessTokenExpiresAt` 字段（建议 24 小时）。
- **应急**：token 通过 HTTPS 传输 + sessionStorage 存储，泄露风险可控。
